# Analytics V2: candidate scoring and selection contract

This document defines the small-batch contract used by `av2-190` and
`av2-200`. A candidate score is an analytical selection signal; it is not a
probability, a quality claim or a recommendation decision.

## Processing order

1. Compute persisted feature observations for the exact excerpt hash.
2. Apply `EligibilityGate` and record the first explicit rejection reason.
3. Require a registered embedding model and a non-null embedding with matching
   dimensions.
4. Apply the supervised scorer only when an artifact is explicitly enabled and
   its checksum/state pass validation.
5. Run deterministic MMR over the eligible candidates.
6. Persist ranker code, version, configuration/artifact hash, components,
   dimensions and final selection score.

The order is fail-closed: an unavailable feature or embedding removes the
candidate from selection rather than turning the missing value into zero.
Tie-breaking uses candidate ID, so a replay with the same input and model
version is deterministic.

## Scorer promotion

`EXCERPT_SUPERVISED_SCORER_V1` artifacts generated by
`scripts/train-candidate-scorer.py` start as `EXPERIMENTAL`. They must not be
changed to `VALIDATED` by automation. Promotion requires a versioned human
acceptance report, a work/author-safe holdout evaluation, the artifact hash and
an explicit reviewer. Until then the worker remains on the heuristic ranker by
default, or uses the experimental scorer only in a controlled test.

## Small-batch acceptance

The minimum controlled acceptance is 8--32 books, with persisted rank rows and
the following evidence:

- no missing or mismatched embedding model;
- rejection counts by explicit reason;
- stable selected IDs on replay;
- rank components and scorer hash present when the scorer is enabled;
- no mutation of catalog language or source text.

This acceptance does not replace the human-quality gate or authorize a bulk
500-book run.

## Fail-closed invariants

The Java pipeline rejects a candidate before MMR when its feature status is not
`VALID`, its embedding is absent or empty, its model identifier differs from
the registered model, or its vector dimension differs from the first eligible
vector in the batch. Rejection reasons are returned as stable machine-readable
codes and must be counted in the batch report. This prevents a malformed
embedding from silently becoming a zero-similarity candidate.
